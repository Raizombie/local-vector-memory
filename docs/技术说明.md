# 技术说明

面向想读代码或改代码的人。使用说明见根目录 `README.md`。

## 目录结构

```
index.js                    入口：身份日志、注册 5 个工具、启动后台调度
lib/env.js                  身份与路径（HANA_HOME 从 dataDir 反推；agentId 从 sessionPath 认领）
lib/config.js               设置读取与 worker 参数翻译
lib/worker.js               spawn python worker（解释器探测与缓存）
lib/runtime.js              工具/路由/定时器共用的状态：配置、worker 通道、补全
lib/scheduler.js            后台调度：事件驱动（主力）+ 定时兜底，全程写日志
tools/                      5 个 agent 工具
routes/settings.js          设置页后端（/status /maintain /probe /search /config /python）
ui/panel.html + assets/     状态 / 体检 / 检索测试 / 设置
python/vector_memory.py     真正碰 facts.db 的那一层（标准库，零依赖）
skills/local-vector-memory/ 给 agent 的用法说明
```

## 为什么 sqlite 的活在 python 子进程里

v2 App 的 JS 跑在宿主的 Node 权限模型下：安装目录只读、只有 `app-data/<id>` 可写。
连 `fs.existsSync("<HANA_HOME>/agents/...")` 都会被拒。而 spawn 出来的子进程**不继承**这层限制。

所以分工是：JS 负责编排（读设置、注册工具、起定时器、拼路径），所有碰 `facts.db`
的活（建表、补嵌入、检索）都交给 `python/vector_memory.py`——stdin 收一份 JSON，
stdout 吐一份 JSON，stderr 当日志。只用标准库（`sqlite3` / `urllib` / `array`），
不需要 pip 安装任何东西，也就不需要 `better-sqlite3` 那种原生模块编译。

## 数据

复用 v1 插件的表结构与向量格式，**已有向量不需要重嵌**：

- `fact_embeddings(fact_id, model, dims, vector, content_hash, created_at, updated_at)`
- `fact_embedding_jobs(fact_id, reason, queued_at, attempts, last_error)`
- 三个触发器：facts 插入/更新自动入队，删除时连带清掉向量与队列项

比 v1 多的两点：

1. 检索时按 `model + dims` 过滤，队列也会把"属于旧模型"的行重新排进去。换嵌入模型后
   不会静默地拿两种向量空间互相比余弦，跑一次 backfill 就自动重建。
2. worker 开库时额外设 `PRAGMA foreign_keys = ON`，与触发器形成双保险。

## 检索与打分

两路召回后融合：

- **关键词**：FTS5 + 中文 bigram（复用 v1 的查询构造），按排名归一化
- **语义**：查询向量与库内向量的余弦
- **融合**（`fusion` 设置项）：
  - `minmax`（默认）：先把两路分数各自在候选集内线性拉伸到 0–1，再加权；
    权重 `0.65 / 0.20 / 0.10 / 0.05`（语义 / 关键词 / 标签 / 新近度）
  - `linear`：直接加权相加，权重 `0.55 / 0.30 / 0.10 / 0.05`（旧行为，可回退）

  为什么要归一化：语义余弦实际只在 0.3–0.5 这一小段活动，关键词排名分却铺满 0–1。
  直接相加等于让量纲大的那个说话。实测（6 个查询）：

  | 配置 | 命中 top1 |
  |---|---|
  | linear 0.55/0.30 | 5/6 |
  | minmax 0.65/0.20 | **6/6** |

  失手的那条查询里，语义最高的一条（0.759）在 linear 下连前六都进不去，归一化后直接第一。

  注：`ftsCandidates` 保持 200 不动。实测收窄到 40 / 30 没有额外收益，反而会让
  "语义极相关但字面不匹配"的条目丢掉关键词分。

## 后台调度

两种触发方式，各有独立开关（`autoMaintain` / `eventDriven`），都在 `lib/scheduler.js`，
由 `applyModes()` 按当前设置统一启停（改完设置调它即可，旧名 `reschedule`）：

1. **事件驱动**：订阅 `turn_end` / `message_end`。收到后**延迟 10 秒**再扫
   （`EVENT_SETTLE_MS`）——memoryTicker 也是回合结束后才开始蒸馏写库，去早了空手。
   这 10 秒内若又来事件则重新计时（去抖），避免一轮排好几个任务。
2. **定时轮询**：按 `maintainIntervalMs`（默认 600000 = 10 分钟）定时扫一遍，
   覆盖“信号丢了”和“不经对话写入”两类意外。

两个开关互相独立：都开、只开一个、都关都合法。此外 **每次 App 启动会先扫一次积压**
（与两个开关无关），每次调用检索工具还会顺手触发（30 秒节流）；都关时只剩这些加手动按钮。

每一次启停都会把当前组合写进日志（`补全方式：回合结束触发=…，定时轮询=…`），
一眼能看出跑的是哪种、有没有退化成纯手动。

每一轮动作与失败都写日志（`[vector-memory]` 前缀），这是刻意的：**原 v1 插件就死在
"失败了但没人看得见"**。

## 为什么是从零重做的

原 v1 插件 `hanako-local-vector-memory`（群友 pathos 的作品）的后台补嵌入**从来没执行过**。根因：

- 插件的 `onload` 由 `onStartup` 触发，那一刻 ctx 里没有 `agentId`；
- `getVectorConfig` 的 agentId 回退链是「本地配置 → ctx.agentId → 字符串 `"hanako"`」；
- 于是它去开 `agents/hanako/memory/facts.db`，而那个目录不存在，`openFactsDb` 抛错；
- 异常被 `onload` 的 catch 吞掉，而它写日志用的 `ctx.log` 在该宿主里不存在；
- 结果 `startAutoDrain` 从未注册，60 秒定时器压根没存在过——只能靠人在会话里手动跑 backfill。

旁证：库里二十多个 job 的 `attempts` 全是 0（从未被尝试过），几个 agent 库的覆盖率长期
停在 60%~98% 不等，还有一个连向量表都没建起来。

这个 App 的做法是不再猜单个 agent：直接扫 `agents/*/memory/facts.db` 全部过一遍。

### 什么情况下它其实能正常工作

这个 bug 不是所有机器上都会发作，条件很具体：

- 用户的 agent 目录里**存在名为 `hanako` 的记忆库**（也就是单 agent、且用了默认名）；
- 或者手动在 `plugin-data/hanako-local-vector-memory/config.json` 里写死了 `agentId`。

满足任一条，生命周期路径就能找到库，定时器也就注册得上了——这大概也是原作那边没发现这个问题的原因：
单 agent 配置下它确实是好的。

**但即使如此，第二种情况也只补那一个 agent 的库**：定时器只认一个固定路径，其他 agent 的记忆
永远不会被自动补上，还是得手动跑工具。也就是说，只要你是多 agent 用户，无论怎么配都只能手动补。

另外，**工具路径一直是正确的**——在会话里手动调用 `search_memory_plus` / `memory_vector_backfill` 时，
ctx 带着当前 agentId，路径算得对。所以受影响的自始至终只有“后台自动补嵌入”这一条链路。

## 改完代码怎么生效

源码在工作区 `G:\OH-WorkSpace\sora\local-vector-memory`，而 Hana 实际跑的是安装副本
`<HANA_HOME>/apps/local-vector-memory`。v2 App 没有热重载，改完要走三步：

1. **同步到安装副本**。App 的 JS 读不到工作区，只认安装目录，所以改哪个文件就拷哪个：

   ```powershell
   Copy-Item "G:\OH-WorkSpace\sora\local-vector-memory\lib\scheduler.js" `
             "$env:USERPROFILE\.hanako\apps\local-vector-memory\lib\scheduler.js" -Force
   ```

   改多个文件就直接 robocopy 整个目录覆盖（排除 `__pycache__`）。
2. **重载实例**。对本 App 执行 reload。只要 manifest 没新增 capability / network 权限，
   重载不会弹确认，几秒就完；新增权限就得重新过一遍审核。
3. **看日志确认**。搜 `[vector-memory]`，启动那行会带 `HANA_HOME` 和当前补全方式
   （`回合结束触发=…，定时轮询=…`），一眼能判断新代码有没有真的跑起来。

一个容易踩的点：`python/vector_memory.py` 改完不需要 reload——worker 每次都是新起的子进程。

## 出包

两种包，用途不同：

- **解压即用包**：把 `local-vector-memory` 整个目录压成 zip（顶层就是目录名），
  别人解压后丢进 `<HANA_HOME>/apps/`。注意先删掉 `python/__pycache__`。
- **官方格式包**（可给 App Manager 导入）：先用 `--archive` 验证，再用打包脚本生成；
  这种格式要求 manifest 在 zip 根目录，不是外面套一层。

```sh
node <hana>/scripts/validate-app.mjs --dir <项目目录> --json
node <hana>/scripts/extension-pack.mjs --kind app --dir <项目目录> --publisher <名字> --out <输出目录>
```

## 验证方式

```sh
node <hana>/scripts/validate-app.mjs --dir <this dir> --json
```

开发时的运行期验证：用假 ctx 直接调 `apply()`，看日志与工具返回（harness 脚本不入包）。
