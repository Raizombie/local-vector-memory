# 本地向量记忆（Local Vector Memory）

给 HanaAgent 的记忆库加一层**本地向量索引**：让你的 agent 能按"意思"而不只是按"字面"想起你说过的事。

原本 Hana 的记忆检索只有关键词（FTS5）那一路。**当查询和目标记忆一个实词都不重叠时，它基本是失灵的。**举个结构上最常见的场景：库里存着「用户每周打三次羽毛球」，你问「他喜欢什么运动」——「羽毛球」和「运动」在字面上毫不相干，关键词通道给这条记忆 0 分；而另一条仅仅因为都含「什么」两个字而被匹配上的无关记忆却能拿到满分，于是排到了前面。

（实测过这种情形：目标记忆的语义分是全场最高的 0.482，却只排第二；第一名是一条语义相关度为零的记忆，`sem=0.000`，只靠 `fts=1.000` 上榜。做完量纲对齐之后，那条目标记忆以 0.658 回到第一，紧随其后的也都是语义上真正相关的记忆。）

---

## 依赖

- **HanaAgent ≥ 1.0.6-beta**（v2 App 体系）
- **Python ≥ 3.9**，只用标准库，**不需要 pip 装任何东西**
- 一个 OpenAI 兼容的 embedding 服务：
  - 本地：LM Studio（默认 `http://127.0.0.1:1234/v1`）、Ollama、vLLM
  - 云端：SiliconFlow、OpenAI 等

## 安装

1. 解压出 `local-vector-memory` 文件夹，整个放进 `<HANA_HOME>/apps/`
   （Windows 默认 `C:\Users\<你>\.hanako\apps\`）
2. 重启 Hana
3. 界面上会弹安装确认，同意即可。它要两个权限：
   - `app/tools.expose-to-model`（把工具给模型用）
   - `app/process.spawn`（启动本地 python 干活）
4. 把这个 App 启用给你想用它的 agent

## 配置

打开「本地向量记忆」的面板（设置里的那一项，或它的卡片），填三样：

| 项 | 说明 |
|---|---|
| Embedding 服务 | LM Studio 就是 `http://127.0.0.1:1234/v1` |
| 模型 | 必须和 LM Studio 里的模型 id **一字不差**（含 `@q8_0` 这类后缀） |
| 维度 | 跟模型对应（bge-m3 / Qwen3-Embedding-0.6B 都是 1024） |

其余保持默认即可。填完点「全部补全」跑一次，把已有记忆补上向量。

### ⚠️ 中文用户请务必注意嵌入模型的选择

**不要用 `nomic-embed-text-v1.5` 这类纯英文模型。** 实测它把不同的中文句子压成几乎相同的向量：

- 改写句（“用户喜欢喝什么” ↔ “用户爱喝什么饮料”）平均相似度 **0.764**
- 无关句（"用户喜欢喝什么" ↔ "今天股市怎么样"）平均相似度 **0.767**
- 差值 **−0.002** —— 等于完全没有区分度，语义通道不但没用，还会往排序里灌噪声

换成多语言模型后同一个测试：

| 模型 | 维度 | 改写句 | 无关句 | 差值 |
|---|---|---|---|---|
| nomic-embed-text-v1.5 | 768 | 0.764 | 0.767 | **−0.002** ❌ |
| Qwen3-Embedding-0.6B | 1024 | 0.715 | 0.334 | **+0.381** ✅ |
| bge-m3 | 1024 | 同样可用 | | |

面板上的「跑体检」按钮随时可以自测：改写句相似度必须明显高于无关句。

## 装完就能用的东西

给 agent 5 个工具，你平时不用手动调：

- `search_memory_plus` — 语义 + 关键词混合检索（agent 问"以前说过什么"时会用）
- `memory_vector_status` — 各 agent 的覆盖度、运行状态、最近错误
- `memory_vector_backfill` — 手动补全；**换嵌入模型后用它重建**
- `memory_vector_probe` — 嵌入模型体检
- `memory_vector_configure` — 直接改配置

### 自动补全的两种方式（可以分别开关）

**① 回合结束触发**（默认开）

订阅 Hana 的回合结束信号（`turn_end` / `message_end`）。收到后**延迟 10 秒**再扫一次——
这十秒是留给 memoryTicker 的，它也是回合结束后才开始把对话蒸馏成记忆，去早了是白跑。
这期间又来事件会重新计时，所以一轮里连发几个事件也只补一次。优点是**新记忆几秒内就能被语义搜到**，
而且**空闲时完全不动作**。

**② 定时轮询**（默认开，默认间隔 10 分钟）

按固定间隔扫一遍所有记忆库，只做“有没有缺向量”的检查，没活就直接退出。
它兜的是两种意外：**信号本身丢了**（宿主没发、或 App 重启后订阅没挂上），
以及**压根不经对话写进来的记忆**。

怎么选：

| 组合 | 适合谁 | 代价 |
|---|---|---|
| 两个都开（默认） | 大多数人 | 空闲时每 10 分钟起一个短命 python 进程（几十毫秒） |
| 只开回合结束 | 想省资源、且只在这个 Hana 里聊天 | 信号丢了没人兜，新记忆可能一直不带向量 |
| 只开定时轮询 | 宿主版本较旧、或用了非标准入口写记忆 | 语义检索最多晚一个间隔才看到新记忆 |
| 两个都关 | 想完全手动控制 | 只有启动时和手动点「全部补全」才会补 |

另外无论怎么设：**App 启动时会先补一次积压**，每次调用检索工具也会顺带触发一次（30 秒节流），
界面上还有「全部补全」按钮可以随时手动跑。

## 数据与安全

- 你的记忆仍然存在原来的 `facts.db` 里，这个 App 只加了两张**旁车表**（`fact_embeddings` / `fact_embedding_jobs`）。删掉 App 不影响任何记忆正文。
- 所有数据库操作在本地 python 子进程里完成，不联网。
- 只有调用 embedding 服务时才发请求；配本地 LM Studio 就是完全离线。
- 记忆被删或修改时，触发器会让向量自动跟着删/重算，不会留孤儿数据。

## 已知限制

- **换嵌入模型后必须跑一次 `backfill` 重建**（App 会自动把"属于旧模型"的向量判为过期重嵌，不用手动清）。
- 事件驱动依赖宿主的会话事件广播；如果你把「定时轮询」也关了，信号一丢就没人兜底。
  拿不准就两个都开，成本很低。
- 嵌入模型的绝对能力有上限：像"表达感谢"和"表达认可"这种细粒度区分，模型本身分不清，排序算法救不了。

## 关于仓库里的 `sdk/`

`sdk/` 是从 Hana 宿主同步出来的 SDK 副本（脚手架生成的依赖，不是本项目源码），所以**没有提交到仓库**。
安装包不受影响：Release 附件里的 zip 是**包含** `sdk/` 的。

想从源码构建：用 Hana 自带的 `scripts/sync-app-sdk.mjs` 把这台机器上的 SDK 同步进来即可。

## 在原作基础上做了什么

**修复**

- **后台自动补嵌入从来没执行过**。原插件的 `onload` 由 `onStartup` 触发，那一刻拿不到 `agentId`，
  回退到不存在的 `agents/hanako/memory/facts.db`，异常又被静默吞掉（它写日志用的 `ctx.log`
  在宿主里根本不存在），于是那个 60 秒定时器从未注册成功过——只能靠人在会话里手动跑 backfill。
  （顺带说：**单 agent、且 agent 名正好是 `hanako` 的配置下它是能正常跑的**，
  大概也是原作那边没发现这个问题的原因；但多 agent 用户无论怎么配都只能手动补。）
- **失败不再无声**。所有动作与错误都写进宿主日志（`[vector-memory]` 前缀），
  不会再出现“插件加载成功但什么都没干”。

**新增**

- **扫全部 agent**：不再依赖单个 agentId，直接遍历 `agents/*/memory/facts.db`，
  一次把所有 agent 的记忆库都照顾到。
- **模型版本守卫**：检索按 `model + dims` 过滤，队列会把属于旧模型的向量重新排进去。
  换嵌入模型不会再静默地拿两种向量空间比余弦。
- **量纲对齐融合（minmax）**：语义与关键词先在候选集内各自归一化到 0–1 再加权，
  语义通道不再被关键词的量纲盖住。**这是原插件没有的一层**——原插件的做法就是直接加权相加
  （相当于本项目的 `linear` 模式）。拿同一组 6 个查询在两种模式下做内部对照：linear 5/6、minmax 6/6。
- **嵌入模型体检**：一眼看出当前模型对中文有没有区分度（就是上面那张 nomic 的对照表）。
- **两种可切换的补全触发**：回合结束信号触发（延迟 10 秒）+ 定时轮询，各有独立开关，
  可只开一个；不再是死板轮询。
- **设置面板**：覆盖率、体检、检索测试、参数改动都在界面上做，不用改文件。
- **可解释检索**：每条命中带 `semNorm` / `ftsNorm` / 标签 / 新近度分解，方便排查。

更细的原理、目录结构和“为什么 sqlite 活在 python 子进程里”见 `docs/技术说明.md`。
